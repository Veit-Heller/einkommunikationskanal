01 — Vision

Was ist das Produkt?

Ein CRM für Versicherungsmakler, das sich über einen eingebetteten KI-Coding-Agenten per Chat anpassen lässt. Der Nutzer beschreibt was er will. Der Agent schreibt den Code, deployed eine Preview, der Nutzer genehmigt — und die Änderung ist live.

"Ich will meine Kontakte in Gruppen clustern nach Produkttyp." → 3 Minuten später ist das Feature live.

🧠

Kein Code sichtbar

Der Nutzer spricht Deutsch, der Agent schreibt TypeScript. Alles passiert im Hintergrund.

👁️

Preview vor Live

Jede Änderung wird zuerst als Vorschau deployed. Erst nach Genehmigung geht es live.

🔄

Automatisches Git

Sinnvolle Commits, Branches, automatischer Push. Die Versionshistorie ist immer sauber.

🏗️

Eigene Instanz

Jeder Kunde hat seinen eigenen GitHub Repo + Vercel Deployment. Keine geteilte Infrastruktur.

02 — Wie es funktioniert

Der Flow

1

Nutzer schreibt eine Anfrage im CRM-Chat

"Ich will auf der Kontaktkarte sehen, welche Versicherungsprodukte der Kunde hat."

2

Agent analysiert die Codebase

Liest relevante Dateien aus dem GitHub Repo des Kunden via GitHub API. Versteht Kontext, Datenbankschema, bestehende Komponenten.

3

Agent plant und schreibt den Code

Claude API mit Tool Use: read_file, write_file, create_branch, commit. Mehrere Dateien, saubere Commits, TypeScript-konform.

4

Preview Deployment

Vercel deployed den Branch automatisch als Preview-URL. Nutzer sieht die Änderung live bevor sie in Production geht.

5

Genehmigen oder Ablehnen

Nutzer klickt "Übernehmen" → merged nach main → live. Oder "Ablehnen" → Branch gelöscht, nichts passiert.

6

Production Deployment

Vercel deployed automatisch. Innerhalb von ~2 Minuten ist die neue Version live. Keine Downtime.

03 — Technische Architektur

Wie es gebaut wird

🤖

Claude API (Anthropic)

claude-opus-4 mit Tool Use. System-Prompt kennt die Codebase-Struktur, Verbote, und Stilregeln.

🐙

GitHub API

Lesen & Schreiben von Dateien, Branches erstellen, Commits, Pull Requests — alles ohne Server-Clone.

▲

Preview Deployments pro Branch. Build-Status abrufen. Merge triggern wenn Build grün.

05 — MVP

Was braucht man zum Starten?

Das MVP ist nicht das fertige Produkt — es ist das Minimum um zu beweisen dass das Konzept funktioniert und die ersten Kunden zu gewinnen.

💬

Chat-UI im CRM

Einfache Chat-Oberfläche im CRM mit Nachrichtenverlauf. Nutzer kann Wünsche eingeben.

🔧

Agent Backend

API-Route die Claude aufruft mit GitHub-Tools. Liest Dateien, schreibt Änderungen, erstellt Branch.

👀

Preview-Link

Zeigt dem Nutzer die Vercel Preview-URL. Knopf "Übernehmen" merged nach main.

🍴

Onboarding-Fork

Neuer Kunde → automatischer Fork des Basis-Repos + Vercel-Projekt + DB. Vollautomatisch.

MVP Nicht-Ziele (bewusst weggelassen)

Kein Billing-System, kein Self-Service Signup, keine Multi-User-Verwaltung, kein App Store für Erweiterungen — das kommt alles nach dem ersten zahlenden Kunden.

06 — Roadmap

Drei Phasen

Phase 1 Proof of Concept 4–6 Wochen
  • Chat-UI im bestehenden CRM einbauen
  • Agent Backend mit Claude API + GitHub Tools
  • Preview Deployment Flow (Branch → Vercel Preview → Approve)
  • Sicherheitsschicht im System-Prompt
  • Erste Tests mit Stevie + Stefan als echte Nutzer
  • 5 erfolgreiche "ich will X" → "X ist live" Durchläufe dokumentieren
Phase 2 Erste externe Kunden 6–10 Wochen
  • Automatisches Onboarding: Fork + Vercel + DB auf Knopfdruck
  • Billing (Stripe) — einfaches Monatsabo
  • Onboarding-Flow für neue Makler (kein technisches Wissen nötig)
  • 3–5 Beta-Kunden aus dem Maklernetzwerk gewinnen
  • Agent-Gedächtnis: CLAUDE.md pro Kunde wird automatisch aktualisiert
  • Fehlerbehandlung wenn Build fehlschlägt
Phase 3 Produktisierung 3–6 Monate
  • "Erweiterungs-Bibliothek": häufig angeforderte Features als 1-Klick-Installationen
  • Andere Branchen erschließen (Steuerberater, Anwälte, Immobilien)
  • Multi-User pro Instanz mit Rollen
  • Agent-History: alle gemachten Änderungen mit Rollback-Option
  • Marketplace: Nutzer können Erweiterungen teilen und verkaufen
  • White-Label: andere SaaS-Anbieter können den Agenten in ihre Produkte einbetten

09 — Risiken

Was kann schiefgehen?

Hoch

Agent macht Production kaputt

Mitigation: Branch-Only, Build muss grün sein vor Merge, automatische Rollback-Option, tägliche DB-Backups.

Hoch

Claude API Kosten skalieren schlecht

Mitigation: Caching häufiger Anfragen, Rate-Limiting pro Plan, teurere Plans haben mehr Budget.

Mittel

Nutzer-Anfragen sind zu komplex für den Agent

Mitigation: Klares Fehler-Feedback, Scope-Limits, "kann ich nicht" Antworten mit Erklärung.

Mittel

Vercel / GitHub API Abhängigkeit

Mitigation: Abstraktionsschicht die auch andere Deployment-Targets unterstützt (Railway, Fly.io).

Niedrig

Lovable / Bolt kopieren die Idee

Mitigation: Vertikale Tiefe (Versicherungsmakler-spezifisch) ist schwer zu kopieren. Distribution und Kundenvertrauen sind der Moat.
